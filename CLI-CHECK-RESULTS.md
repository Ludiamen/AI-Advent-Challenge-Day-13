````
# Ревью фичи 0920-0224 «Слой колодцев на карте»

Сверял три результата (архитектор, backend, фронтенд) между собой, с рамками проекта, с инвариантами и с тем, что реально известно о legacy. Ниже — расхождения по убыванию критичности.

## 1. Нарушение инварианта «1С — источник истины»: Django-ORM как редактор колодцев

- **Что написано.** В backend-результате модель `Well` описана как обычная Django-модель с `BigIntegerField(primary_key=True)` и `external_id`. В архитектурном результате прямо сказано: «Django-ORM на запись используется внутри обработчиков `ЗаписатьОбъектВГИС` / `УдалитьОбъектИзГИС` / `ПолнаяСинхронизация`, но не как самостоятельный редактор колодцев».
- **В чём расхождение.** В присланном фрагменте backend-кода нет ни одного из этих обработчиков, нет запрета на запись (например, переопределённого `save()` с проверкой контекста, отдельного менеджера только для чтения, отсутствия `ModelAdmin` на запись). Модель выглядит как полноценная редактируемая сущность. При этом фронтенд-результат отправляет правки геометрии через WFS-T GeoServer — то есть **в обход 1С и в обход Django**.
- **Чем грозит.** WFS-T GeoServer пишет напрямую в `gisdata.well`. Это ровно тот сценарий, который инвариант запрещает: бизнес-объект попадает в `gisdata`, минуя 1С. При следующей `ПолнаяСинхронизация` из 1С запись либо будет перезатёрта, либо породит конфликт по `external_id`. Для диспетчера это выглядит как «правка пропала».
- **Что нужно.** Либо WFS-T публикуется только на чтение (`<Transaction>` выключен в GeoServer), а правки идут через Django-эндпоинт, который вызывает 1С-интеграцию; либо WFS-T разрешён только для слоёв, не являющихся бизнес-объектами 1С. В текущем виде это не оговорено ни в одном из трёх результатов.
````

</details>
